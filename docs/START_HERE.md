# 先掌握项目，再阅读文件

你可以把这个项目看成六个系统合作，而不是一大堆Java类：

| 玩家问题 | 系统 | 设计位置 |
|---|---|---|
| 我能学什么、怎么学 | 魔法书与学习 | spec/learning |
| 我按键以后何时释放、何时中断 | 施法 | spec/casting |
| 魔力从哪里来、如何保存 | 玩家数据 | spec/player |
| 发出的魔法命中后发生什么 | 魔法 | spec/magic |
| 方块、传送、核心、召唤怎样与世界交互 | 世界规则 | spec/world |
| 我看见什么、听见什么 | 视觉表现 | spec/visual |

“水弹能造成多少伤害”和“塞妮丝书是否能直接学水弹”是两个设计，通过water_ball这个ID关联，不互相包含。

## 三层怎么读

**intent是为什么**：希望还原什么体验、有什么取舍。这里不写类名和构建结果。

**spec是什么**：精确到数值、时机、边界和失败结果，能拿来验收。这里不规定必须用哪个Java类。

**impl是怎么做**：代码职责、路径、设计模式和测试位置。可以重构而不改变玩法规则。

以水弹为例：[目标](intent/MAGIC.md) → [设计卡](spec/magic/spells/water_ball.md) → [真实代码追踪](impl/WATER_BALL_WALKTHROUGH.md)。先看这一个例子，不用先看102种术。

## 你如何掌握和修改项目

1. 先说希望玩家体验如何变化，例如“火焰像喷流，不像白色管子”。
2. 找到负责的系统；这例主要改视觉合同和资源，不改伤害或魔法书。
3. 用标准变更卡写出前后差别与验收画面；AI据此定位代码。
4. 看STATUS判断代码和测试到了哪里，再决定是否进行游戏验收。

新增一术只复制[法术模板](development/templates/SPELL.md)，按[流程](development/WORKFLOW.md)完成设计、关联、实现和验证。你不必背Java文件树，重要的是能判断改动属于哪个系统、应该改哪条规则、怎样证明改好了。

## 文件数量为什么仍不止几份

102术卡是可单独查询的设计实例，不要求你或AI一次读完。模板规定格式，实例保存具体设计；共同规则不复制进每张卡。STATUS只存当前情况，logs只存过去发生的事，archive不参与日常开发。
